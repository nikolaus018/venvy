A sceptical pass over the whole codebase, with weight on what v5 added (containers, routes,
previews, app backups, platform). Every finding below was reproduced (a script or a test that
fails before the fix) or is pointed to by line, with the scenario that goes wrong. Ranked by
severity. Status says what happened to it; tests are named where they live.

Baseline before any change: `tests/run_all.sh` → 32 of 33 suites pass; **ui** fails (finding 4),
also when run alone.

## 1. Routes expose any localhost port on a public hostname (High)

`venvy/api/platform.py` `add_route` / `put_route` and `venvy/api/apps.py:845` (the port check in
`PUT /apps/{id}`).

v4.9.5 made the **domain** field check that the app's port is really the app's
(`_check_publish_port`): otherwise an operator could point a public hostname at Venvy's own port,
another app's port, or a database that listens on 127.0.0.1 because it trusts the host. Routes
(Hosting → Routes, v5) forward a hostname to the very same port, and nothing checks it: the PUT
check only runs when the app has a `domain`.

Reproduced: an operator sets an app's port to the port of a local HTTP service that is not the
app's; `PUT` with a domain answers 409 "Something other than this app is listening", `PUT` without
one answers 200, `POST /apps/{id}/routes` answers 200, and `GET /` with `Host:` the route's hostname
returns the private service's page through Venvy's proxy.

Fix: adding or changing a proxy route runs the same check, and so does changing the port of an app
that has proxy routes. Test: `tests/t_review_2611.py` ("a route can't point at a port that isn't
the app's").

## 2. A deploy counts as ok before the app answers (High, known problem 1)

`venvy/deploy.py:764` `_wait_healthy`.

With no health check configured, a deploy is "ok" once the app is still running 6 seconds after
the restart. For a Compose app "running" is the `docker compose up` process, which runs while the
containers are still starting; in production the site answered 502 for a while after a deploy
reported ok. Any web process that dies or never binds after 6 s is reported the same way.

Fix: a deploy is ok only once the app answers. With a configured check, that check (as before).
Without one, a web process that listens (its own process tree, or its containers' published ports;
see 3) must answer on its port with something other than 502/503/504 (a TCP service that isn't
HTTP counts once it accepts and answers); a process that listens on nothing (a worker, a bot), or an app
whose health check is set to None on purpose, keeps the old rule. A container app is waited for until its containers are up; if they publish no port, running is enough.
Otherwise the deploy is rolled back. Tests: `tests/t_review_2611.py` ("a deploy whose app answers
502 is rolled back", "a worker that listens nowhere still deploys"), and the real-Docker CI job (12).

## 3. Port ownership answered in five places (Medium, known problem 2)

`venvy/api/cloudflare.py:266` (`_app_ports`) and `:342` (`_check_publish_port`), `venvy/process.py:823`
(`_launch_port_free`), `venvy/process.py:1705` (the supervisor's port scan), `venvy/deploy.py:764`
(deploy health), `venvy/api/system.py:304` (ports in use), `venvy/firewall.py:57`.

Each looked at a different subset: the supervisor only at the process tree, so a Compose app's
`detected_ports` stayed empty and a second published port could never be published through the
tunnel ("Port … is not one of this app's ports"); System → Ports in use named an app only for
`App.port`, so container ports and extra ports showed no app (and a restricted operator didn't see
them at all); start-up cleaned containers on any busy port without asking whose it was.

Fix: `venvy/ports.py` answers it once: `claimed(app)` (port, manual, seen), `listening(app)` (what
the app holds right now: process tree, or its containers' published ports for docker/compose) and
`holder(port, app)` ("self", "other app", "something else", or free). Tunnel publish, domains and
routes, start-up, the supervisor's scan, deploy health, free-port search and System → Ports all use
it. Tests: `tests/t_review_unit.py` (fake `docker` and fake listeners), `tests/t_platform_unit.py`
(existing launch tests still pass).

## 4. Two apps are handed the same port (Medium)

`venvy/process.py:246` `find_free_port`.

A free port is one nothing *listens* on (plus a 10 s memory). An app that has a port but doesn't
listen (stopped, a worker, still starting) loses it to the next app that starts more than 10 s
later. Reproduced by the existing UI suite: Alpha (a loop) gets 8001; Beta starts later and gets
8001 too; saving a domain for Alpha then fails with "Port 8001 is also another app's port" (409).
That is why `ui` failed before this review, alone or side by side.

Fix: ports claimed by other apps are skipped too (`ports.claimed`). Test: `tests/t_review_unit.py`,
and `ui` passes again.

## 5. Compose files checked while the old containers still run (Medium)

`venvy/process.py` `_start_app_process`: `compose_guard.pinned_argv` (render + check) ran first,
`_docker_cleanup` (compose down) after.

The check resolves every bind mount with `realpath`; the daemon resolves the path again when it
creates the container. The app's old containers are still running during the check, and they can
write to the app's folder (it is bind-mounted into them). Between the check and `up`, a container
can replace a checked directory with a symlink to `/`; the new container then gets the host's root
mounted. Fix: the old containers are removed *before* the file is rendered and checked, so nothing
of the app runs between the check and `up`. Test: `tests/t_review_unit.py` (order of the calls).

Not changed, for you to decide: a container that Docker itself restarts (`restart: always`) is
mounted again by the daemon without Venvy looking. Closing that means forcing `restart: "no"` in the
checked copy and letting Venvy restart the whole project, which changes how Compose apps behave
when one service crashes. Listed under "Decisions".

## 6. Container apps: limits and egress shown as set but not applied (Medium)

`venvy/launcher.py:159-195`, `venvy/runtimes.py:588` (`docker_run_argv`), `venvy/compose_guard.py`.

For a Compose app, the memory, CPU and process limits are set on the systemd unit of the
`docker compose` CLI; the containers run under the Docker daemon, outside that unit, so no limit
applies to them. The egress policy is skipped for every container app (`not as_root`), and a Docker
app with a port ignores "deny". Settings shows the limits without the "not enforced" warning
(`resource_limits_enforced` is true).

Fix: the checked Compose copy gets `mem_limit`, `cpus` and `pids_limit` on every service that
doesn't set a lower one itself (per container, as Docker apps already do). An egress policy other
than "allow" is refused for Compose apps and for Docker apps with a port, with a message that says
why; an app that already has one logs at start that it isn't enforced. Tests: `tests/t_review_unit.py`.

## 7. App-backup settings restore can make an app a Compose app (Medium)

`venvy/appbackup.py:160` (settings restore) and `venvy/api/platform.py` `restore_app_backup`.

`POST /apps/{id}/backups/{name}/restore` with `settings: true` is for operators and sets every field
of the backup's `app.json` on the app, without the rules `PUT /apps/{id}` applies. Only an admin may
make an app a Compose app (`runtimes.ROOT_RUNTIMES`: compose runs through the Docker daemon, as root).
An operator restoring an old backup of an app that was once a Compose app turns it into one again,
and controls its compose file. Fix: a settings restore by a non-admin that would change the runtime
to one of those is refused (403); restoring only the files still works. Test:
`tests/t_review_2611.py`.

## 8. A failed app-backup restore leaves the app stopped (Medium)

`venvy/appbackup.py:150`.

The app is stopped, then the archive is unpacked; if unpacking (or a swap) fails, the function
raises and the app stays stopped, with the half-unpacked folder left in its state folder. The
docstring promises "a failed restore leaves the app as it was". Fix: on any failure after the
stop, the work folder is removed and the app is started again if it was running. Test:
`tests/t_review_2611.py` (a corrupt backup).

## 9. Preview domains collide (Low)

`venvy/previews.py:83`.

A preview's domain is `<label>.<preview domain>`, with no check: branches `feat/x` and `feat-x`
get the same domain, and a branch named after an existing app's subdomain, or Venvy's own address,
gets that hostname. Fix: a label already used by an app, a route, the tunnel or Venvy itself gets a
short suffix. Test: `tests/t_review_unit.py`.

## 10. A compose `container_name` can take another app's name (Low)

`venvy/compose_guard.py` (no rule for `container_name`), `venvy/telemetry.py:398` (metrics by name),
`venvy/process.py:800` (`docker rm -f venvy-app-N`).

A Compose service with `container_name: venvy-app-5` blocks Docker app 5 from starting, is removed
when app 5 starts, and its usage is counted as app 5's. Fix: a `container_name` must start with the
app's own project name. Test: `tests/t_platform_unit.py` (compose rules).

## 11. Restricted operators and global objects (Low)

`venvy/api/platform.py` `put_monitor`, `del_monitor`, `list_volumes`.

Monitors belong to no app; an operator limited to some apps could change or delete the admin's
monitors, including the public ones on the status page. `GET /volumes` lists which app ids use each
volume, including apps the user has no access to. Fix: changing or deleting monitors needs an admin
or an operator with access to all apps; the volume list shows only the apps the user may see. Test:
`tests/t_review_2611.py`.

## 12. No real Docker in CI (known problem 3)

`.github/workflows/ci.yml`. All container tests use a fake `docker`. Fix: a `docker` job on
ubuntu-latest (Docker is installed there) runs `tests/t_docker.py`: it creates a small Compose app,
deploys it from an artifact, restarts Venvy and checks that the app keeps its port and its route,
and deploys a broken version that must be rolled back while the site keeps answering.

## 13. Hosting → Run and build → Build command is never saved (Medium)

`web/static/js/hosting.js:76` (`RUN_FIELDS`) and `venvy/api/apps.py` (`UpdateAppReq`, `SPEC_FIELDS`).

The Hosting tab saves its Run and build card with `PUT /apps/{id}`, build command included; that
request has no `build_command` field, so the value is dropped without an error and the card says
"Saved". The next deploy runs the old build command (or none). Only the Deploy tab's field (`PUT
…/git`) worked. Fix: `PUT /apps/{id}` takes `build_command` (same rules as `PUT …/git`). Phase 3
leaves one field for it (decision 1). Test: `tests/t_review_2611.py`.

## 14. Docker builds fail when Venvy doesn't run as root (Low)

`venvy/isolation.py:233` (`_clean_root_env`), used for the build steps Venvy runs itself
(`docker build`, `docker compose build` / `pull`, `venvy/deploy.py:275`, `venvy/process.py:721`).

That environment is made for root's wrappers and always says `HOME=/root`. When Venvy is not root
(a `--shared-user` install with Docker access, or CI), the Docker CLI can't read its config there
and doesn't find a Compose plugin installed for its user: found by the new real-Docker CI job,
where every Compose deploy failed with `unknown shorthand flag: 'p' in -p`. Fix: the home of the
user Venvy runs as (`/root` as root, as before). Test: `tests/t_review_unit.py`, and the Docker job.

## 15. Saving a domain with other settings waits 20 s and loses its audit entry (Medium)

`venvy/api/apps.py` `update_app`. Found while checking the new UI, present in v5.0.5 too (measured:
21.7 s on both). The handler sets fields on the app row, then queries (for a domain change: is the
name taken?); SQLAlchemy flushes the pending changes first, which takes SQLite's write lock. The
audit entry for the domain change is then written from a connection of its own, waits out the
20-second busy timeout and is dropped ("database is locked"). The Settings save sends every field
at once, so changing a domain from the UI took over 20 seconds, and the change was missing from
Activity. Fix: the handler's audit entries are written after its commit. Test:
`tests/t_review_2611.py`. The other handlers write theirs after a commit already (checked with a
script over every function that does both).

## 16. "Clear All" ports throws (Minor)

`web/partials/tabs/settings.html` (now `network.html`) calls `checkSettingsDirty()` from a
`data-on-click`, which only runs allow-listed functions; it wasn't on the list, so the button
cleared the field and then threw, and the Save button didn't show unsaved changes. Fix: allow-listed.

## 17. "Logs" on a worker opens the default tab (Minor)

`web/static/js/hosting.js` (Processes) called `selectApp(id, 'logs')`; `selectApp` takes an
options object and ignored the string. Fix: a tab name is accepted. Test: covered by `t_ui.py`
(an old `settings` link and tab names go through the same path).

Authorisation on every route (the router-level `require_app_access`, admin-only platform routes),

## Decisions taken

- **Docker restarting Compose containers by itself** (see 5): not changed. Forcing `restart: "no"`
  would make every container start go through Venvy's check, but a crashed service would then stay
  down until Venvy restarts the whole project, and the one Compose app in production may rely on
  per-service restarts. The case needs a container that is already compromised (root in its own
  namespace) in a Compose app, which only an admin can create; README says so plainly. Revisit if
  Compose apps are ever given to non-admins.
- **Candidates for removal** (other servers, database replication, log shipping, OTLP, ngrok,
  preview apps, commit statuses, Tailscale Funnel): all kept in the backend, as the brief requires.
  In the UI each is one line until it is set up (decision 10), so unused ones cost nothing.
- **Decision 7, replication vs off-site backups:** both kept, side by side under System → Backups,
  whose first card says in plain sentences which of them run (and that no automatic backup runs,
  when that is so). Folding replication into the backup schedule would change what the API stores.
- **Decision 9, monitors vs health checks:** done through the subtitles: Health says monitors are
  for things outside Venvy, Monitors says an app's own check is in its Health tab.
