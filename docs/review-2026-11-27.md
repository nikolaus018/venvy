# Review, 2026-11-27 (v5.1.0)

A pass over the whole backend and frontend after the v5.1 UI reorganisation. Static checks first
(ruff with the pyflakes, bugbear, pylint-error and async rules over `venvy/`, `scripts/` and `tests/`;
ESLint over the UI's scripts concatenated in the order `web/index.html` loads them; a cross-check of
every `data-on-*` handler, element id and ARIA reference in the partials), then a read of the parts
that face the network without a login: the domain proxy and its routes, port forwards, push webhooks,
the public status page, artifact deploys, the terminal, the file manager, setup and login.

Every finding below was reproduced (a test that fails before the fix) or is pointed to by line, with
the scenario that goes wrong. Ranked by severity. Tests are in `tests/t_review_2711.py` unless named.

Baseline before any change: `tests/run_all.sh` → every suite passes.

## 1. The proxy sends gzip to clients that never asked for it (Medium)

`venvy/proxy.py` `_http_inner`.

The upstream request is made with aiohttp, which adds `Accept-Encoding: gzip, deflate` to a request
that has none. The proxy's session runs with `auto_decompress=False` and passes the body on as it
comes, `Content-Encoding: gzip` included. So a client that sent no `Accept-Encoding` (curl without
`--compressed`, many monitoring checks, bots, simple HTTP libraries) got compressed bytes from any
app that compresses by itself (most frameworks' gzip middleware, nginx inside a container). aiohttp
also put its own `User-Agent` on requests that had none.

Reproduced: an upstream that gzips when asked; `GET` through `DomainProxyMiddleware` without
`Accept-Encoding` answered `Content-Encoding: gzip`.

Fix: the upstream request skips aiohttp's automatic `Accept-Encoding` and `User-Agent`, so the app
sees the client's own headers. Test: "a client without gzip gets plain text".

## 2. The proxy cache serves one client's encoding or variant to another (Medium)

`venvy/proxy.py` (cache key) and `venvy/routing.py` `cache_ttl`.

The key held whether *Venvy* gzips (`rule.gzip` and the client accepting gzip), not what the client
accepts. With the route's own gzip off and an app that compresses by itself, the first client's
gzip (or br) answer was cached under "no gzip" and served to every later client, including ones that
can't decode it. Separately, a response with `Vary: Cookie`, `Vary: Accept-Language` or `Vary: *` was
cached under a key that holds none of those, so one visitor's variant went to the next.

Fix: the key holds the encodings the client accepts (br, deflate, gzip, zstd); a response that varies
on anything but `Accept-Encoding` is not cached. Tests: "cache: Vary …", "the same encodings again come
from the cache".

## 3. A route's basic-auth password can be guessed without limit (Medium)

`venvy/routing.py` `basic_auth_ok`.

Hosting → Network → a route's basic auth is checked with scrypt in a worker thread, with nothing
counting failures; the route's rate limit is optional and off by default. Anyone could guess as fast
as the host runs scrypt, and keep the default thread pool (which every `asyncio.to_thread` in Venvy
shares) busy doing it. An unknown user name was answered at once, so the answer time told which names
exist.

Fix: ten wrong passwords per route and client address in a minute; past that every attempt from
there is refused without being checked, until the minute has passed. An unknown name is checked
against a dummy hash, so it takes as long as a wrong password. Tests: "basic auth: …".

The limit is per client address as Venvy resolves it (`CF-Connecting-IP` through the tunnel, the TCP
peer otherwise). Where every visitor arrives from one address — a proxy in front of Venvy that it
doesn't trust — someone guessing can keep a route's other visitors out for a minute at a time; those
who signed in within the last five minutes are not affected (their check is remembered).

## 4. An artifact upload stops the whole server while it is checked (Medium)

`venvy/api/platform.py` `deploy_artifact`.

After an upload (up to `_ARTIFACT_MAX`) the archive was read through with `tarfile` to check its
entries, on the event loop. That decompresses the whole archive: for a large build output, every
request (the UI, the proxy for every app, webhooks, the terminal) waited for it. A client that hung up
during the upload left the part written in `releases/incoming/`.

Fix: the check (`_check_artifact`) runs in a thread, writes go through a thread too, and the file is
removed whatever stops the upload. Tests: "artifact: …".

## 5. The public status page is counted afresh on every request (Low)

`venvy/telemetry.py` `status_data`, `uptime`.

`/status` and `/status.json` need no login. Each answer ran two counts over up to 30 days of samples
for every item, twice (24 h and 30 days), in the request thread pool. Anyone could ask as often as
they liked.

Fix: one answer serves every request for ten seconds (the page reloads once a minute); a changed
setting shows at once. The two counts per period are one query. Tests: "status page: …".

## 6. UDP forwards open one upstream socket per datagram while the first is opening (Low)

`venvy/forwards.py` `_UdpFront`.

A client's first datagram started a task that opens its upstream socket; datagrams that arrived
before it was open each started another. Every one but the last was dropped from the table and never
closed (a socket leak per burst). The tasks were not kept (an asyncio task with no reference can be
collected while it runs), a failure to open was an unretrieved exception, and closing the forward
left a socket being opened behind.

Fix: one pending socket per client, with what arrives meanwhile queued (64 datagrams at most) and sent
once it is open; tasks are kept and cancelled on close. Tests: "udp forward: …".

## 7. Unpacking an artifact can hang a deploy for ever (Low)

`venvy/deploy.py` (artifact unpack).

The archive was written into `tar`'s stdin with a blocking read on the event loop and an unbounded
`drain()`; only the final `communicate()` had the 20-minute limit. A `tar` that stops reading (a full
disk, an app user with no quota left) held the deploy, and the app's deploy lock, for ever. Fix: the
whole feed and wait run under the one limit, reads happen in a thread, and a `tar` past it is killed.

## 8. A changed route password kept working for five minutes (Low)

`venvy/routing.py` `basic_auth_ok`.

A successful check was remembered by the exact `Authorization` header for five minutes, to skip
scrypt. Changing or removing that user's password did not end it. Fix: the remembered check holds the
hash it was made against and counts only while that is still the stored one. Test: "the old password
stops working once changed".

## 9. A control character in a route header breaks every response (Low)

`venvy/api/platform.py` `_clean_route`.

Extra response headers were checked for CR, LF and NUL only. Any other control character is
accepted by the form and refused by the HTTP layer when the response is sent, so every request on
that route failed. Fix: control characters other than tab are refused when the route is saved.

## 10. Two UI paths still looked for the Settings tab v5.1 removed (Minor)

`web/static/js/shell.js` (polling), `web/static/js/auth.js` `applyRoleUiGating`.

v5.1 spread the old Settings tab over Overview, Deploy, Network, Config and Health. Two places still
asked for `#tab-settings`: polling never refreshed the unsaved-changes marker from the server any more,
and a viewer's settings fields were no longer disabled (the API refuses the change; the form looked
editable). Both now use `SETTINGS_TABS`.

## 11. Leftovers (Minor)

- 28 unused imports in `venvy/`, 17 in `tests/`, five unused variables in the UI scripts.
- The Code tab named `tab-code` in `aria-controls`, which doesn't exist; it now names the pane it shows.
- `PUT /apps/{id}` stored `manual_ports: [8000, 8000]` as two ports.
